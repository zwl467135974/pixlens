# 06 经验沉淀：踩坑与解法实录

> 来源：v1.1（2026-09-21）用户实测反馈驱动的修复，核心战场是 PSD/PSB Explorer 缩略图扩展。
> 每条按「现象 → 根因 → 解法 → 预防」组织，供后续开发与同类项目复用。

## 一、Windows Shell 扩展（COM 缩略图）

### 坑 1（本批最大）：1MB 栈数组 × DllHost 小线程栈 = 必现栈溢出

**现象**：缩略图 DLL 在 PowerShell / Explorer 主进程中一切正常，但在 **DllHost.exe**（Shell 的 COM 代理进程）中加载即崩，异常码 `0xc00000fd`（STACK_OVERFLOW）。该现象穿过了三种独立实现：Rust `#[implement]` 宏版、Rust 手写 vtable 版、C++ 手写版——极具迷惑性。

**排查弯路**（记录以避重蹈）：二分排除了 rayon、memmap2、image crate、宏实现、LTO、CLSID 被 COM 拉黑等七个假设，均烟雾弹。

**根因**：读文件流的缓冲写成了 `unsigned char buf[1 << 20]`（1MB **栈**数组）。Explorer 主进程线程栈 8MB 无恙；DllHost 的 COM 线程栈远小于 1MB，函数入口的 `__chkstk` 栈探测直接溢出。三版实现共用同一段读流逻辑，故同点崩溃、崩溃偏移稳定。

**定位手段**：`dumpbin /disasm` 反汇编崩溃偏移 `0xADC7`，看到 `lea r11,[r11-1000h]; mov byte ptr [r11],0` 的栈探测循环 + 崩溃函数头部 `call __chkstk`——一锤定音。

**解法**：栈数组改堆分配（`std::vector` / `Vec`）。一行修复，全部样本通过。

**预防**：**COM 进程内服务器（任何会被 DllHost/svchost 加载的 DLL）禁用大栈数组**，>64KB 的缓冲一律堆分配。code review 时对 `[N]` 形式的局部数组保持敏感。

### 坑 2：Rust staticlib 链入 C++ DLL，其运行时初始化与 CRT 在 DllHost 冲突

**现象**：C++ 壳链接 Rust `staticlib`（哪怕函数体是空桩）在 DllHost 中栈溢出；同样的 Rust 代码编成独立 `cdylib` 由 C++ 运行期 `LoadLibrary` 加载则完全正常。

**根因**：staticlib 会把 Rust std 的静态初始化段（lang_start/堆/TLS）合并进宿主 DLL，与 C++ CRT 的初始化在受限代理进程中冲突。

**解法**：**Rust 代码永远编成独立 cdylib，C++ 壳 `LoadLibrary` + `GetProcAddress` 动态调用**。两个 DLL 各自独立初始化，互不污染。附带好处：可独立更新解码核心。

**架构结论**（本项目最终形态）：C++ COM 壳（~250 行，纯系统依赖）+ Rust cdylib 解码核心 + 系统 GDI+ 解内嵌 JPEG，三层各司其职。

### 坑 3：COM IID 手抄错误

**现象**：Shell 探测接口后静默放弃（错误码 `0x8004B200`），无任何调用。

**根因**：手写 IID 常量多处抄错——`IID_IUNKNOWN` 写成全零 GUID（导致 QI(IUnknown) 失败、Shell 判定对象非法直接销毁）；`IInitializeWithFile` 与 `IInitializeWithStream` 的 IID 张冠李戴。

**解法**：**永远从本地 windows crate 源码核对 IID**（`~/.cargo/registry/.../windows-*/src/` 里 grep `define_interface!`），不要信记忆。

### 坑 4：手写 COM 的"视图指针"偏移陷阱

**现象**：QI 返回的 `IInitializeWithFile` 接口指针调用 `Initialize` 后对象状态错乱（数据读到偏移内存）。

**根因**：一个 C++/Rust 对象暴露多个接口时，非主接口的指针指向**结构体中段**的 vtable 成员（如 `&this.file_vt`），把它当对象首地址访问字段即错位。

**解法**：每个视图的 QI/AddRef/Release/方法入口先做指针归一化：`self_ = (p - offsetof(Struct, file_vt))`（Rust 用 `std::mem::offset_of!`）。或者像 C++ 版那样直接用**多继承**让编译器生成正确的 thunk。

### 坑 5：改完 handler 后 Explorer 仍显示旧图标

**根因**：Windows **缩略图缓存**（`%LOCALAPPDATA%\Microsoft\Windows\Explorer\thumbcache_*.db`）命中旧结果，不会因 DLL 更新而失效。

**解法**：测试循环中固定动作——`taskkill explorer → 删 thumbcache_*.db → 重启 explorer`。**测试验证不要依赖 Explorer 肉眼观察**：用 `IShellItemImageFactory::GetImage`（PowerShell P/Invoke）以编程方式提取，它与 Explorer 走完全相同的加载路径且可断言返回值。

### 坑 6：C++ COM DLL 的导出——DEF 文件"静默失效"与 STDAPI 冲突

**现象**：`/DEF:` 指定导出文件但导出表为空；`__declspec(dllexport) STDAPI` 报重定义/语法错。

**根因**：DEF 路径在批处理续行块中被吞；`STDAPI` 宏已含 `extern "C"`，前面再加 `__declspec(dllexport)` 违反声明顺序；且系统头 `combaseapi.h` 已声明这两个函数，签名不匹配即报"只是返回类型不同"。

**解法**：在定义之后用 `#pragma comment(linker, "/export:DllGetClassObject")` 链接器指令导出（x64 下 extern "C" 无名称修饰）。**注意 NSIS 的 `BUILD_OK` 类判断要先删旧产物**，否则链接失败的旧 DLL 会造成假成功。

### 坑 7：手写 DllMain 覆盖了 Rust/CRT 默认入口

**现象**：DLL 加载即崩，任何代码（包括入口第一行日志）都执行不到。

**根因**：给 Rust cdylib 手写了 `DllMain`，覆盖了工具链默认入口，跳过 std 堆/TLS 初始化。

**解法**：**cdylib 永远不要手写 DllMain**。需要初始化用 `#[ctor]` 注入 .init_array。

### 坑 8：UTF-8 中文注释 × GBK 代码页 → 语法错误雪崩

**现象**：MSVC 编译报几十个不知所云的语法错误（从中间某行开始全线崩坏），同时批处理 rem 注释里的中文被吞出 `'/PSB' 不是内部或外部命令`。

**根因**：源文件 UTF-8 无 BOM，MSVC 默认按系统 GBK 代码页解析，中文注释字节流被误切分，破坏了后续语法结构。

**解法**：编译加 **`/utf-8`**；批处理文件只用 ASCII 注释。

## 二、构建与分发

### 坑 9：MSVC CRT 动态链接的分发陷阱

**现象**：开发机一切正常，发给别人（干净系统）打不开。

**根因**：Rust（MSVC target 默认）与 C++（cl 默认 `/MD`）都动态链接 `vcruntime140.dll`，干净系统没有它。

**解法**：
- Rust：项目 `.cargo/config.toml` 加 `[target.x86_64-pc-windows-msvc] rustflags = ["-C", "target-feature=+crt-static"]`
- C++：编译加 `/MT`
- 验证：`dumpbin /dependents <exe|dll>` 检查导入表**只剩系统库**（kernel32/gdi32/ole32 等）。

**预防**：面向分发的 Windows 项目，交付前跑一遍依赖检查应成为固定动作。

### 事实（非坑）：无签名安装包的 SmartScreen

个人开发者代码签名证书成本高（每年数千元），无签名包首次运行会弹"已保护你的电脑"，用户点"更多信息→仍要运行"即可。文档/README 中应提前告知用户。

## 三、开发环境互操作（Git Bash / cmd / PowerShell / 注册表）

### 坑 10：`cmd /c start` 在 Git Bash 下的引号转义 → 用户可见弹窗

**现象**：自动化测试反复在用户屏幕弹出"Windows 找不到'\\'文件"。

**根因**：Git Bash（MSYS）对 `cmd //c 'start "" "路径"'` 的引号与反斜杠转义规则与预期不符，路径被拆坏。

**解法**：**从 Git Bash 打开资源管理器一律用 PowerShell**：`powershell -Command "Start-Process explorer.exe -ArgumentList '路径'"`。自动化测试更要如此——错误命令的弹窗会直接骚扰用户。

### 坑 11：PowerShell 写注册表 `(default)` 默认值的不可靠性

**现象**：`reg add`/`Set-ItemProperty` 报"成功"但默认值未写入，或产生键名带引号的坏键（`InprocServer32"`）。

**解法**（按可靠度排序）：
1. `.reg` 文件 + `reg import`（注意必须 ANSI/UTF-16 编码，UTF-8 无 BOM 会部分行失效）
2. `[Microsoft.Win32.Registry]` .NET API 的 `CreateSubKey + SetValue('', value)`
3. 写入后**必须回读验证**——本批中"假成功"出现过三次。

### 坑 12：`grep`/`sed`/python-heredoc 在此环境的稳定性

会话中 python heredoc 的 `str.replace` 多次静默不生效（打印 ok 但文件未变）。**补丁类操作后必须 `grep` 验证命中**，或直接用编辑器工具。sed 正则同样需要验证。

## 四、调试方法论（这次真正起作用的手段，按效果排序)

1. **`dumpbin /disasm` 定位崩溃偏移**——本批的终局手段。事件日志给出"崩溃模块 + 偏移"，反汇编该偏移附近即可看到崩溃现场的指令语义（我们的案例：栈探测循环），配合函数符号（`/Zi /DEBUG` 生成 pdb）直接指认真凶。
2. **Windows 事件日志（Id=1000）**——确认"哪个模块崩 + 异常码 + 偏移"，区分"真崩溃"与"被拒绝"。`Get-WinEvent -FilterHashtable @{LogName='Application'; Id=1000}`。
3. **`%TEMP%` 日志文件注入**——在被调试 DLL 的每个入口写日志，区分"没被调用"与"调用了但失败"（两种失败的处理方向完全不同）。DllHost 与宿主进程写同一文件（按 PID 区分）。
4. **程序化复现路径**——把"肉眼看 Explorer"替换为 `IShellItemImageFactory` 的 P/Invoke 调用：可断言、可循环、可进 CI。
5. **依赖二分**——同壳换依赖逐个剔除（空壳 crate、stub 函数），快速缩小"代码问题 vs 依赖问题"。注意：**二分结论必须可复现三次以上**再采信（本批曾因单次侥幸得出错误结论）。
6. **从本地 crate 源码核对 API 真值**——IID、接口方法槽位、vtable 布局，`~/.cargo/registry` 里的生成代码就是权威文档。

## 五、一句话总结

> 一个 1MB 栈数组，借 DllHost 的小栈藏了七层烟雾弹；最终破案靠的是"崩溃偏移 + 反汇编"这对老实工具。
> 而所有环境层的坑共同指向一条纪律：**每个写操作都要回读验证，每次"成功"都可能是假的。**
